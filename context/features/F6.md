# F6 — Improve (with permission)
## Goal
Fix issues safely: recommend, configure, preview, approve, apply as a new version, and undo.
## Depends on
F0, F4, F5.
## Inputs / Outputs
`GET /issues/{id}/recommendations`, `POST /actions`, `GET /actions/{id}/preview`, `POST /actions/{id}/approve`, `POST /actions/{id}/apply`, `POST /versions/{id}/restore`.
## User flow
Review recommended action -> Configure (e.g. fill with median, drop duplicates keep first) -> Preview before/after and rows affected -> Approver confirms -> Apply as new version -> Undo or restore any time.
## Business rules
- Raw/parent version is never modified (checksum proves it).
- Only role Approver/Admin can approve and apply. A proposer cannot approve their own action (configurable).
- Preview row count must equal applied row count.
- Applying creates version n+1 with `parent_version_id`; restore re-points "latest", never deletes versions.
- Concurrent applies on the same dataset are serialised (lock) or rejected with a clear message.
- Action types v1: drop duplicates (keep first/last), fill nulls (median/mean/mode/constant), standardise category case/mapping, null-out invalid values, trim whitespace. Start with drop duplicates only for the MVP.
## Out of scope
Free-form transformations, scripting, scheduling.
## Acceptance criteria
1. Parent version checksum identical before and after apply.
2. Preview `rows_affected` == applied `rows_affected`.
3. Analyst calling approve/apply gets 403.
4. Undo/restore yields data identical (checksum) to the earlier version.
5. Audit log shows who/what/when for propose, approve, apply, restore.
6. Two simultaneous applies do not corrupt data or create duplicate version numbers.
7. After dropping planted duplicates from `golden_dirty`, re-assessment shows uniqueness issue resolved and row count == 1000.
## Tests required
Unit (each action), integration (approval flow, restore), concurrency test, golden (end state matches `golden_clean` for the fixed columns), security review.
